# 整理一个项目的结构

用户说一个项目"乱""不清晰""繁琐", 或要把一份外部材料 (评审表、清单) 放进树里时, 按这里做.

树是帮用户记录的, 不规定必须怎么写. 用户画了或说了怎么摆, 就照原样摆: 标题用原话, 状态不动, 下面的规则不拿来改它. 例: 几个方案画成一条竖线, 表示的是这个方向上探索的深度, 不要改成 FORK.

## 先诊断, 不动手

通读整个项目文件. 先把用户的感觉落成具体的结构问题讲给用户, 再给一份目标骨架 (只写标题层). 用户点头之后才动手.

用人做事时的两种搜索来判断:

- **广度**: 同一种东西, 彼此独立, 谁先谁后都行 (一组需求、几项验收). 平铺成同级兄弟正是它的形状.
- **深度**: 走某一步时冒出来的问题、它的前置、它引出的修复. 它属于那一步, 应该挂成那一步的章节, 有先后的就按先后排.

挂在下面只有两种意思: 是它的组成部分 (章节), 或是查它用的参考. **"为它出了力"只是关联, 不是包含.** 静态表 (需求表、验收表)、实现过程、特性和方案是三件事, 大需求按 SKILL.md「大需求」分成 SR 列表、过程、特性三条线并排放.

| 症状 | 说明 |
|---|---|
| 一张编号清单 (`#1..#N`), 条目性质各异 (前置、疑问、待决策、收尾杂事) | 深度搜索的产物被压平了: 丢了深度、父节点和兄弟间的先后 |
| 同一个广度画了好几遍 (清单的类别、FORK 的支线、需求列表) | 只该留一个广度, 其余是重复 |
| 正文里大量"见 #N""见「…」" | 结构活在文字里, 树上没画出来 |
| 主线顺序和实际走的顺序不同 (总结排在被总结的工作前面, 第一步落在最后) | 主线失真 |
| FORK 的支线是分类, 不是能并排比较的环境或假设, 也不合回 | FORK 被当成了分组 |
| 要做的数目大得不像真的 | 重复节点算了两次; 按清单身份定状态, 而不是按"还要做吗"定; 正文写了结论, 状态没改; `?` 已经有答案, 还是 TODO; 不用特别关注的后续任务也标了 TODO |
| 同一步实现在两条需求下各有一份; TODO 挂在 HALT 下 (算进要做, 却画成灰的) | 实现过程挂进了静态表: 实现和需求是多对多, 树只能给一个父节点; 需求的状态是"验过没有" (DONE), 实现的是进度 (HALT) |

能用数字说明的就用数字: 交叉引用有几处、重复节点有几对、TODO 和 HALT 各几个.

## 往哪放

- 外部材料本身 → 一条 REF (原文路径、快照信息). 它的编号、栏目、分类、证据等级不带进树里
- 需求、验收项 → SR 列表那条线, 同级平铺; 下面只挂验证步骤
- 实现过程 → 过程那条线, 按日期分段, 一件事一张卡: 做了什么、commit、结果
- 实现时冒出来的问题、TODO → 过程线上那一步下做章节
- 方案和考虑 → 特性那条线; 几个方案按探索先后一条竖线. 只放用户手写的, AI 写的分析不放
- 只是分组的标题 (下面是几件事, 本身没有要做的) → 走完了标 HALT, 还在走就不写状态; 写 HALT 会把下面的 TODO 画灰
- 评审、表外验收、回归、整理 PR、补文档 → 过程线末尾. 三条线不合并 (FORK 后面不放东西), 除非用户要
- 还没答案的事 → `?`
- 等某次会议或某个人拍板的事 → 那次会议做过程线上的一步, 待定的事做它下面的 `?`
- 已经说了本次不做的 → HALT
- 和主线完全不相干的另一件事 → 项目开头的 FORK 里另一条支线 (见 SKILL.md)

状态重新定: 做过的步骤、正文里已有结论的、已决定暂不做的, 都是 HALT; 验过的 SR 是 DONE; 需要特别关注的是 TODO, 其余没做的是记录.

## 动手

- 记下基线: `git -C ~/.dsh/mainline log -1 --format=%h -- <文件>`. 确认 `git -C ~/.dsh/mainline status --porcelain <文件>` 为空; 不为空说明有未提交的编辑, 就把当前文件复制一份 (写成 Windows 路径) 当基线.
- 重复的节点: 内容并进**旧**节点 (保留旧 id), 删掉新的. 删节点就是丢掉一个 id, 所以删除和大范围移动都要先得到用户同意.
- 大改结构可以整文件 Write. 写之前确认文件在你读过之后没变 (status 为空, 修改时间没变).
- 改完对着基线检查. 插件几秒内就会自动提交, 所以要比基线, 不能比 HEAD:

  ```sh
  node ~/.claude/skills/todo-mainline/check.mjs ~/.dsh/mainline/<文件> <基线>
  ```

  它报告: 往返是否一致、id 是否唯一、删掉和新增了哪些 id、标题层改了哪些节点. 删掉的 id 必须都是说好要删的.
- 结果里有你没做的改动时, 先查 `.mainline/events.jsonl`. `actor.kind` 为 `human` 的是用户在面板上改的: 不要当成错误还原, 告诉用户.
- 用户在面板上清空的正文、写下的原话, 搬动时原样带走, 不要从旧版本里把内容补回去. 动之前比一遍每个旧节点的正文 (基线 vs 新文件), 有差异的逐条确认是有意的.

## 精简正文

结构定下来之后再精简正文. 正文多时交给一个上下文干净的子 agent (用户的建议: 上下文干净, 质量更高). 交代给它:

- 只改正文: 标题、id、顺序、状态都不动; 觉得标题该改, 只列建议
- 删什么、留什么, 按 SKILL.md「正文怎么写」
- 先记基线, 改完跑 check.mjs, 标题层必须一处没变
- 汇报内容: 检查输出、删了哪几类 (各举两三个例子)、有意丢掉的事实、建议改的标题

子 agent 交回后, 自己再通读一遍, 然后向用户汇报.
