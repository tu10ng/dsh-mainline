# 工作树 (dsh-mainline)

用户把工程工作记成攻略: 主线是要沿着走的步骤, 分叉是并排的几条支线 (两套环境、两个竞争的假设), 走完合回主线; 参考是挂在步骤上查的东西 (命令、代码位置、寄存器值、链接、文档), 不算主线. 树里有**很多个项目**, 互不相干: 不要把一个项目的上下文带进另一个; 一句话不知道属于哪个项目时先问.

## 在哪

- 目录 `~/.dsh/mainline/` (Windows 上是 `%USERPROFILE%\.dsh\mainline\`; 设了 `DSH_HOME` 时是 `$DSH_HOME/mainline`). 一个项目一个 `.md`, 顺序在 `mainline.json`.
- 直接用 Read / Edit 改文件. dsh-mainline 插件会发现外部编辑, 面板自动刷新, 并自动 git 提交; dsh-web 没开时, 下次启动补提交.
- **用户此刻在看哪**: `ls -t ~/.dsh/mainline/.mainline/view/` 第一个 `<项目id>.json` 是面板上最近操作过的项目 (项目 id 是 H1 上的 `{#id}`), 其中 `selected` 是选中节点的 id (`null` = 没选). 点选后约 1 秒写盘. 用户说"这一步""这里"时以它为准; 拿不准就问.
- 最近发生了什么: `.mainline/events.jsonl` 每行一个事件, `summary` 是一句中文.

## 格式

标题层级就是树的层级: 项目 `#`, 它的孩子 `##`, 依此类推, 超过 6 层就继续加 `#`. 节点正文是标题到下一个标题之间的文字.

```
#…  [TODO|HALT|DONE] [REF|FORK] [?] 标题 {#id key="value"}
```

- 状态四种 (括号里是面板上的颜色):
  - 不写 = 记录.
  - `TODO` (粉红) = 需要特别关注的, 不限个数. 不用特别关注的不标 TODO, 即便是后续要做的任务.
  - `HALT` (橙黄) = 进度: 这一步走过了 (做完或停下, 不区分). 记下来的步骤大多是做过的, 所以大多是 HALT.
  - `DONE` (绿) = 只用在 SR 这类列表里: 这一项完成 (验过) 了.
  - 不要发明 doing/优先级/截止日期.
- `REF` 参考, `FORK` 分叉, `?` 疑问 (没答案时是记录, 需要特别关注的才标 `TODO`; 答案写进正文后改 `HALT`).
- 谁能放在谁下面: 项目和步骤下 → 步骤/FORK/REF (步骤下的步骤是它的"章节", 一条子主线); FORK 下 → 支线/REF, 非 REF 的标题都是支线, 不写标记; 支线下 → 步骤/FORK/REF; REF 下 → 只有 REF, 不写标记.
- 一个 FORK 之后的同级步骤 = 各支线合回后的下一步. FORK 后面 (往外层看) 什么都没有时, 各条支线各自走到底, 不合并.
- 每一层都一样, 没有"唯一的主线": 项目里另起一件不相干的事 = 在项目开头放一个 FORK, 原来的步骤整块下移两级放进第一条支线 (起个名), 新事放进第二条支线. 例:

```markdown
# LWD {#lwd0}

## REF 设计文档 {#lwdr1}

## FORK {#k2pq}

### A2 验收 {#m7vd}

#### HALT A2 四机部署与拉起 {#lwds4}

### 另一件事 {#x9fb}

#### 它的第一步 {#c3tn}
```
- 项目 H1 可带 `cwd="D:/path"`, 是卡片上命令的工作目录.

```markdown
## TODO ? mpu 是否也跑这个函数 {#q7ka}

## FORK 两个猜想 {#f2mw}

### 只有 lpu 跑 {#l8re}

#### 在 lpu 上加打印确认 {#s0dn}

### REF 调用链 {#r3xp}
```

## 规矩

- **id 不能改、不能删、不能复用**: 面板、事件和历史都靠 id 认节点. 新节点自己起一个: 4 位 `[a-z0-9]`, 先 grep 确认文件里没有.
- 保持规范排版: 标题后空一行再写正文, 每个标题前空一行, 文件以一个换行结尾.
- 正文里不在代码块中、以 `#` 开头的行要写成 `\#` (否则会变成标题). 标题本身以 TODO/HALT/DONE/REF/FORK/? 开头又不是标记时, 写成 `\TODO …`.
- 移动一个节点 = 移动它整个块 (直到下一个同级或更浅的标题), 并把块里每个标题的 `#` 数一起调整.
- 用 Edit 做小范围修改, 不要用 Write 重写整个文件 (面板或 DSH 会话可能刚改过). 失败就重新 Read 再改. 整理结构时的例外见 [restructure.md](restructure.md).
- 不碰 `.mainline/` (锁、视图、会话、事件日志). 不自己 `git commit`, 永不 reset/rebase/amend. 恢复旧版本: `git -C ~/.dsh/mainline show <rev>:<文件>` 取出内容再写回, 它会成为一次新提交.
- 新项目: 新建一个 `.md`, 首行 `# 标题 {#id}`. 删项目 (删文件) 先问用户.

## 记在哪

- 结果、结论、命令输出 → 对应步骤的正文, 或在它下面挂一条 REF;
- 新冒出来的疑问 → 一个 `?` 步骤 (需要特别关注才标 `TODO`);
- 两个竞争的假设、两套环境 → FORK, 不要塞进同一段正文;
- 一步做完 → 改成 `HALT`, 正文留一句结论.

## 大需求: SR 列表、过程、特性三条线

要评审、要验收的大需求 (范例 `lwd.md`), 一律这样分工. 项目开头放一个 FORK, 分三条支线并排, FORK 后面不放东西: 三条线各自走到底, 不合并. 新建时就搭好; 整理旧项目时也往这三条线归.

- **SR 列表**: 静态的需求表. 支线下只有一个「SR列表」步骤, 每条 SR 是它下面平铺的子步骤; SR 下只挂验证它的步骤 (测了什么、数字). 实现、问题、方案都不放这里. SR 验过了标 `DONE`, 本次不做的 `HALT`, 没验过的不写状态; SR 下的验证步骤做完标 `HALT`.
- **过程**: 真实发生的实现过程, 按时间一条线. 按日期分段 (「10-24 A3 边云拉起」), 段下一件事一张卡: 做了什么、commit、结果. 走过的分段和段下的事都标 `HALT`; 正在走的分段不写状态 (写了 HALT 会把里面的 TODO 画灰). 某一步冒出来的待办挂在那一步下; 往后要做的 (评审、性能、表外验收、合入) 接在线的末尾. 这些都是记录, 需要特别关注的才标 TODO. 不放竞争方案的 FORK, 不放考虑. 从 issue、笔记整理时只取事件和 commit, 不取分析.
- **特性**: 需求涉及的特性和对应的方案, 同时表达广度和深度. 特性横着排: 一个 FORK, 每个特性一条不起名的支线, 支线第一张卡是特性名; 特性再分子特性, 就在这张卡后面再放一个 FORK. 一个子特性下的几个方案按探索的先后画成一条竖线 (深度), 不用 FORK. 只放用户手写的考虑, 状态由用户定.

同一件事可以在三条线上各出现一次, 各写各的: SR 下写验过没有, 过程里写哪天做了什么, 特性下写方案.

## FORK {#j49h}

### SR {#6tvw}

#### SR列表 {#l4xm}

##### DONE [SR] 支持 DP {#ogq7}

##### [SR] 性能达标 {#42tn}

### 过程 {#4wmf}

#### HALT 10-24 A3 边云拉起 {#66xx}

##### HALT 云侧 DP rendezvous 被带到边机，卡死 {#1q2d}

#### 10-30 尾部改走 embedding 反查 {#tsgw}

##### TODO A2 两机 DP2×TP8 验证 {#e4v3}

#### 合入 {#24mp}

### 特性 {#qjpc}

#### FORK {#zmxb}

##### {#ezgk}

###### Engram {#llco}

###### FORK {#w4fc}

####### {#9234}

######## 桶 id {#29k7}

## 正文怎么写

只写标题没说的事. 用户嫌啰嗦已经说过多次, 宁短勿长; 标题说全了, 正文就空着.

- 步骤里只放步骤: 做了什么、commit、结果. 考虑、分析、机制解释、"踩到的几个点"不放进步骤, 也不拆成子步骤. 用户手写的考虑放到特性下面; AI 生成的分析 (包括外部材料里 AI 写的) 不写进树.
- 留: 数字、`文件:行`、commit、命令和参数、报错原文、下一步及其先后、用户做过的决定 (写成"本轮不改", 不写"按用户决定"). 带数据的表格和代码块留着.
- 删: 标签和栏目 (`进展：` `测试过程` `等级：实证`), 外部材料的编号 (`表二 #N`), 重复标题、父节点或兄弟的句子, 树的结构已经表达了的"见「…」", 讲文档自身的话 (状态怎么定的、编号放在哪).
- 标签有实际内容时, 改写成一句话: `推断` → "从未实测", `实证（根因未修）` → "根因未修".

## 整理结构

用户说项目"乱""不清晰""繁琐", 或要把一份外部材料放进树里时, 先读 [restructure.md](restructure.md): 先诊断, 再给目标骨架, 用户同意后才动手, 最后用 `check.mjs` 对着基线检查.

改完用一两句话说改了哪些步骤 (项目 › 步骤), 不复述正文.
